title: Handle errors and retries
description: The three shapes a failure arrives in, how to branch on each, and the five things an agent must never do with one.
---

This guide shows you how to recognise and handle every failure Coffee Chats can return. It covers the three shapes a failure arrives in, how to tell a retry hint from a real failure, and the mistakes that turn a recoverable failure into lost or duplicated work. The [error codes](/mcp/errors) page is the reference table behind it.

## The three shapes a failure arrives in

<Tabs>
  <Tab title="A protocol error">

Every read tool reports every failure the same way:

```json Protocol error envelope
{
  "isError": true,
  "content": [{ "type": "text", "text": "Tool call failed." }]
}
```

There is no code and no reason, and this is deliberate: the reason could itself describe data the connection was not allowed to see. A call to a tool whose permission was not granted arrives in exactly this shape, and so does a write that fails before it produces a result of its own.

Branch on nothing. Report the failure and stop.

  </Tab>
  <Tab title="A result that carries a failure">

The ten safe writes and the five consequential tools answer with a structured result instead, and a failing one looks like this:

```json contacts.notes.update result
{
  "status": "failed",
  "scenario": "conflict",
  "operationId": "0123456789abcdef01234567",
  "error": {
    "code": "VERSION_CONFLICT",
    "retryable": false,
    "correlationId": "0123456789abcdef01234567"
  }
}
```

The `status` field is `failed`, `cancelled` or `uncertain`. The `scenario` field narrows it to `denied`, `expired`, `conflict`, `unavailable`, `cancelled` or `uncertain`. The `code` inside `error` is the thing to branch on, and the [error codes](/mcp/errors) page lists every value it can hold.

  </Tab>
  <Tab title="A retry hint">

A retry hint is not a failure. It never arrives on its own: it rides in the metadata of an answer whose result was accepted, so the whole answer looks like this:

```json Accepted result with a retry hint
{
  "structuredContent": {
    "tag": "accepted",
    "scenario": "loading",
    "operationId": "0123456789abcdef01234567",
    "operationStatus": "processing"
  },
  "_meta": {
    "coffeechats/retry": {
      "code": "PERMIT_BACKPRESSURE",
      "retryAfterMs": 1000,
      "retryable": true
    }
  }
}
```

The result itself sits under `structuredContent` and the hint under `_meta` of the same answer. The call succeeded in being accepted and nothing has been written yet. Wait for `retryAfterMs` milliseconds and call the tool again with the same idempotency key.

  </Tab>
</Tabs>

## Three codes that read differently by tool

`VERSION_CONFLICT`, `ACTION_DENIED` and `ACTION_EXPIRED` have a different cause on a safe write, on a proposal and on a withdrawal, because those tools fail for different reasons. Each tool's own page in the [tool reference](/mcp/tools/overview) prints the wording that applies to it.

`VERSION_CONFLICT` is the one worth spelling out. On a safe write it means either that the stored value moved under the agent, or that the same idempotency key was sent again with different input. On a proposal it means either that the booking page moved between the proposal and the approval, or, again, that the same key was sent again with different input. On `actions.cancel` it means neither of those: the request you asked to withdraw was already decided, already expired or already being applied.

## When a cancelled result is visible at all

A cancelled result after a disconnect is what the mapping produces when the agent can still see the request. After the student disconnects, the agent's credential is dead, so the next protocol call is refused outright rather than answered with `OPERATION_CANCELLED`. Read a refused call as the end of the connection, and expect the structured cancelled result only when the disconnect did not take the credential the agent was using.

A cancelled result from `actions.cancel` is different and always visible, because the agent asked for it on a live connection.

## Five things never to do

<Warning>
Never retry an uncertain outcome under a new key before reading. An uncertain outcome means Coffee Chats cannot tell whether the change landed. A new key is a new change, so retrying under one without reading first can apply the same change twice. [Settle an uncertain result](/mcp/guides/settle-an-uncertain-result) gives the read that settles each write.
</Warning>

Never treat a permitted result shape as one the server produces. The result contract admits shapes that no tool returns today, including the `requires_user_action` tag. A shape being legal is not a promise that anything produces it. Build against the shapes each tool's own reference page lists, and treat anything else as an unrecognised answer to be reported rather than acted on.

Never infer a reason from a read failure. Every read failure is the same fixed text by design. An agent that tries to distinguish a missing permission from a missing record from a temporary fault is guessing, and its guess will be wrong.

Never keep calling a disconnected connection. Once the student disconnects, the protocol call is refused and renewing is refused too. Stop, and ask the student to authorize again if the work still matters.

Never show a raw code to a student on its own. The codes are for the agent. Say what happened and what is stored now.

## Rate limiting is not an error code

A request refused for rate limiting is answered with the status `429` and standard rate-limit headers. None of the published codes appears in that answer. The protocol limiter answers with this body:

```json Rate limit response body
{ "error": "rate_limited" }
```

Honour the retry-after value. A polling loop that ignores it will spend the whole budget on one waiting request and lock the agent out of its own reads. The [limits](/mcp/limits) page states each limit and what it counts.
