---
title: Changes that need approval
description: How an agent proposes a consequential change, hands the student the review link, polls the same tool, withdraws a proposal, and presents each state it can get back.
---

Five tools in the catalogue cannot change anything on their own. They propose a change to the student's booking page, and the change is written only after the student approves it in a browser. This page is the agent's side of that. For the student's side, see [approvals](/mcp/approvals).

The five tools are `booking_update_page_text`, which proposes a new headline and welcome message, `booking_update_page_visibility`, which proposes making the booking page public or private, `booking_update_scheduling_rules`, which proposes the buffer before and after each meeting, the least notice a guest must give and how far ahead the calendar opens, `booking_update_event_type`, which proposes a new title, description and duration for one event type, and `booking_archive_event_type`, which proposes archiving one event type or restoring one that was archived. An event type is one kind of meeting the student offers on the booking page. All five are marked `consequential` in the tool metadata.

## 1. Propose

The agent calls the tool with the values it wants and an idempotency key of 16 to 128 characters. Coffee Chats writes nothing. It creates a request and answers:

```json
{
  "tag": "requires_confirmation",
  "scenario": "loading",
  "operationId": "0123456789abcdef01234567",
  "actionStatus": "pending_approval",
  "handoff": {
    "kind": "action_review",
    "url": "https://mcp.coffeechats.me/actions/0123456789abcdef01234567"
  }
}
```

That is the only answer the agent gets before the student decides. The `operationId` names the request and the handoff URL ends with the same value. The URL is always on `mcp.coffeechats.me` and always has that form. A handoff URL anywhere else did not come from Coffee Chats and must not be opened or shown.

A scheduling proposal carries four bounded integers, and this is what it looks like:

```json
{
  "bufferAfter": 10,
  "bufferBefore": 10,
  "idempotencyKey": "example-idempotency-key-0005",
  "minimumNotice": 12,
  "rollingDays": 30
}
```

The [booking scheduling rules tool](/mcp/tools/booking-scheduling-rules) page states the bound on each of the four. The four rules move together, so send the values you want to keep as well as the ones you are changing.

An event type details proposal names one event type and carries its three fields:

```json
{
  "description": "Bring one question about internships.",
  "duration": 45,
  "eventTypeId": "0123456789abcdef01234567",
  "idempotencyKey": "example-idempotency-key-0008",
  "title": "Career questions"
}
```

The title is 1 to 100 characters, the description 0 to 500, and the duration a whole number of minutes from 5 to 480. The three fields move together, so read the event type with `booking.event_types.get` first and send back the values you are keeping. An empty description clears the description; an empty title is refused, because an event type must have one. A proposal whose three values are already the stored ones is refused as well.

An event type archive proposal names one event type and one boolean:

```json
{
  "eventTypeId": "0123456789abcdef01234567",
  "idempotencyKey": "example-idempotency-key-0009",
  "isActive": false
}
```

`false` archives the event type and `true` restores one that was archived. Proposing the value the event type already stores is refused. So is archiving the only active event type the student has: a student always keeps at least one active event type, and that proposal is refused before any request exists, with the fixed error text every failed read uses.

## 2. Hand the link to the student

The agent cannot approve its own request, and there is no way for it to approve on the student's behalf. Give the student the link and three plain facts: nothing has been changed yet, the link shows exactly what would be changed, and the change happens only if they approve it there.

The review page names the application that asked, marks that name unverified because it is text the application supplied, shows the proposed values in full, and shows the effect, the cost in credits and the recipient list. Do not paraphrase the proposed values in your own words and then send different ones. What the student approves is what the page shows.

## 3. Poll the same tool

There is no status endpoint. The agent calls the same tool again with only the identifier:

```json
{
  "operationId": "0123456789abcdef01234567"
}
```

The answer is the current state of the request. Once the student has approved and the change has been applied, polling returns:

```json
{
  "tag": "completed",
  "scenario": "success",
  "operationId": "0123456789abcdef01234567",
  "operationStatus": "succeeded",
  "result": { "summary": "Booking page text updated", "itemCount": 1 }
}
```

The other four tools return the same shape with their own summary. They are `Booking page visibility updated`, `Booking scheduling rules updated`, `Event type updated`, and, for the archive tool, `Event type archived` or `Event type restored` according to the direction that was approved.

Poll at a human pace. The student has to open a link, read a page and press a button, so a tight loop only spends the connection's request budget, which the [operations](/mcp/recipes/operations) page states.

## 4. Present what comes back

A request is in one of nine places. Each one arrives as a particular shape, and each deserves a different sentence to the student.

| What the agent receives | Where the request is | What to tell the student |
| --- | --- | --- |
| `requires_confirmation`, `actionStatus` of `pending_approval` | Waiting for the student | Nothing has changed. Here is the link; open it to approve. |
| `accepted`, `operationStatus` of `pending` | Approved, not started | You approved it. Coffee Chats has accepted the work and has not started it. |
| `accepted`, `operationStatus` of `processing` | Being applied | The change is being applied now. |
| `completed`, `operationStatus` of `succeeded` | Done | It is done, and it was applied exactly once. |
| `failed` with `VERSION_CONFLICT`, `NOT_APPLIED` or `SERVICE_UNAVAILABLE` | Could not be applied | Say what the code means and what is stored now. The codes are on the [errors](/mcp/recipes/errors) page. An approved archive answers `NOT_APPLIED` when it would leave the student with no active event type. |
| `uncertain` with `OUTCOME_UNKNOWN` | Outcome unknown | Coffee Chats cannot prove whether it landed. Here is what the page says now. |
| `failed` with `ACTION_DENIED` | Declined, or no longer allowed | You declined it, or the connection was no longer allowed to make the change. Nothing was written. |
| `failed` with `ACTION_EXPIRED` | Expired before a decision | The request ran out of time and nothing was written. Ask again if you still want it. |
| `cancelled` with `OPERATION_CANCELLED` | Withdrawn, or revoked before it ran | The request is gone and nothing was written, either because the agent withdrew it or because the connection was disconnected before the change started. |

The two named codes in that list, `ACTION_DENIED` and `ACTION_EXPIRED`, are special cases of a failed result, so match them before the generic failed row.

Two of these look alike and are not. An `accepted` result with `processing` means work is under way and the agent should keep polling. An uncertain result means the work is over and the answer is unavailable, and polling again will not turn it into a yes or a no.

## Withdrawing a proposal

An agent can withdraw a request it made, while the student has still not decided and no work has started. The tool is `actions.cancel`, it takes the identifier and nothing else, and it needs no idempotency key:

```json
{
  "operationId": "0123456789abcdef01234567"
}
```

A withdrawal that succeeds answers with a cancelled result:

```json
{
  "status": "cancelled",
  "scenario": "cancelled",
  "operationId": "0123456789abcdef01234567",
  "error": {
    "code": "OPERATION_CANCELLED",
    "retryable": false,
    "correlationId": "0123456789abcdef01234567"
  }
}
```

Withdrawing a request that is already withdrawn gives the same answer, so a repeat is safe. A request the student has already decided, one that has expired, and one Coffee Chats has already started applying are all past the point of withdrawal, and each answers with a `VERSION_CONFLICT` failing result. Poll the request to find out which of those happened.

A withdrawal reaches only a request the calling connection itself created. An identifier that names anything else is refused with the fixed error text every read failure uses, and that answer says nothing about whether such a request exists.

The student sees a withdrawn request. It leaves the waiting list and appears under the recent decisions on the same page, so a proposal an agent takes back does not simply vanish.

## Editing and re-approval

The review page for a text proposal carries an edit form, and so do the pages for a scheduling proposal and an event type details proposal. If the student changes a value and saves, nothing is written: a new version of the same request is created, and it still needs approving. The identifier does not change, so the agent keeps polling with the value it already has and keeps seeing `requires_confirmation` until the student approves.

The agent is not told what the student edited. If the poll eventually returns a completed result, the values that were written are the ones the student last saw, which may not be the ones the agent proposed. Read the booking page back with `booking.settings.get`, or the event type back with `booking.event_types.get`, before telling the student what it now says.

The visibility proposal has no edit form, because the value it carries has only two states. The event type archive proposal has none either, for the same reason. A student who wants the other direction declines and asks again.

## Expiry

A request expires thirty minutes after it was created. Editing it does not extend that deadline. After it expires, polling returns a failing result with `ACTION_EXPIRED` and nothing was written. Propose again with a new idempotency key if the student still wants the change.

## Revocation in the middle of a request

If the student revokes the connection while a request is waiting or approved but not yet started, the request is cancelled and nothing is written. If the revoke lands after the change has already started, Coffee Chats reports the outcome as unknown rather than claiming it was cancelled, because it cannot prove what that attempt did.

The structured cancelled or unknown result is what the mapping produces when the agent can still see the request. In practice it will usually see neither answer, because a revoke also stops the credential it was polling with, and the next protocol call after a revoke is refused rather than answered. That refusal is the correct signal to stop. Tell the student to look at their booking page, which is the only place the real answer now lives.
