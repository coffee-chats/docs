title: Errors and retries
description: Every failure an agent can receive from Coffee Chats, the exact shape it arrives in, and what to do about each one.

An agent sees failures from Coffee Chats in three different shapes, and they mean different things. This page gives each shape, every code that can appear in it, and the handling each code deserves.

## The three shapes a failure arrives in

One fixed error result, with no code. Every read tool reports every failure the same way:

```json
{
  "isError": true,
  "content": [{ "type": "text", "text": "Tool call failed." }]
}
```

There is no code and no reason, and this is deliberate: the reason could itself describe data the connection was not allowed to see. A call to a tool whose permission was not granted arrives in exactly this shape, and so does a write that fails before it produces a result of its own.

A result that carries a failure. The ten safe writes and the five consequential tools answer with a structured result instead, and a failing one looks like this:

```json
{
  "status": "failed",
  "scenario": "conflict",
  "operationId": "0123456789abcdef01234567",
  "error": {
    "code": "VERSION_CONFLICT",
    "retryable": false,
    "correlationId": "0123456789abcdef01234567"
  }
}
```

The `status` field is `failed`, `cancelled` or `uncertain`. The `scenario` field narrows it to `denied`, `expired`, `conflict`, `unavailable`, `cancelled` or `uncertain`. The `code` inside `error` is the thing to branch on, and the table below lists every value it can hold.

A retry hint beside an accepted result. A retry hint is not a failure. It never arrives on its own: it rides in the metadata of an answer whose result was accepted, so the whole answer looks like this:

```json
{
  "structuredContent": {
    "tag": "accepted",
    "scenario": "loading",
    "operationId": "0123456789abcdef01234567",
    "operationStatus": "processing"
  },
  "_meta": {
    "coffeechats/retry": {
      "code": "PERMIT_BACKPRESSURE",
      "retryable": true,
      "retryAfterMs": 1000
    }
  }
}
```

The result itself sits under `structuredContent` and the hint under `_meta` of the same answer. The call succeeded in being accepted and nothing has been written yet. Wait for `retryAfterMs` milliseconds and call the tool again with the same idempotency key. An agent that treats a retry hint as a failure and gives up abandons work that was going to happen.

## Every code, and what to do about it

| Code | Where it arrives | The cause | What the agent should do |
| --- | --- | --- | --- |
| `VERSION_CONFLICT` | failing result | The value changed after the agent read it, or the same idempotency key was sent again with different input. On `actions.cancel` it means the request was no longer withdrawable. Nothing was written. | Read the value again and make the change from what is there now, with a new key. After a refused withdrawal, poll the request instead. |
| `ACTION_DENIED` | failing result | The student declined the request, or the connection was no longer allowed to make the change. Nothing was written. | Stop. Do not call again. Tell the student the change was refused. |
| `ACTION_EXPIRED` | failing result | The change ran out of time before it started, or the request expired before the student decided. Nothing was written. | Ask once more with a new key, and only if the student still wants it. |
| `NOT_APPLIED` | failing result | Coffee Chats can prove it stopped before writing anything. On an approved `booking_archive_event_type` request it also means the archive would have left the student with no active event type. | The change can be made again with a new key. After a refused archive, read the student's event types again and do not propose the archive until another one is active. |
| `SERVICE_UNAVAILABLE` | failing result | Coffee Chats could not do the work just now and wrote nothing. | Try again later with a new key. |
| `OPERATION_CANCELLED` | cancelled result | On a proposal, the connection was revoked before the change started, so nothing was written. On `actions.cancel` it is the success answer: the request is withdrawn. | After a revoke, stop and ask the student to authorize again. After a withdrawal, tell the student the request is gone and nothing was changed. |
| `OUTCOME_UNKNOWN` | uncertain result | Coffee Chats cannot prove whether the change was written, and will not guess. | Read the value back and treat what is stored as the answer. Do not send the change again under a new key until you have read what is stored. |
| `PERMIT_BACKPRESSURE` | retry hint | Too much work is already running on this connection. Nothing has failed. | Wait for the stated delay and call again with the same key. |
| `PERMIT_CONTENTION` | retry hint | Another call was holding the same slot. Nothing has failed. | Wait for the stated delay and call again with the same key. |

That is every code the connector publishes. A code outside this list is not something Coffee Chats sends.

## Three codes that read differently by tool

`VERSION_CONFLICT`, `ACTION_DENIED` and `ACTION_EXPIRED` have a different cause on a safe write, on a proposal and on a withdrawal, because those tools fail for different reasons. Each tool's own page in the [tool reference](/mcp/tools/overview) prints the wording that applies to it.

`VERSION_CONFLICT` is the one worth spelling out. On a safe write it means either that the stored value moved under the agent, or that the same idempotency key was sent again with different input. On a proposal it means either that the booking page moved between the proposal and the approval, or, again, that the same key was sent again with different input. On `actions.cancel` it means neither of those: the request the agent asked to withdraw was already decided, already expired or already being applied, so the withdrawal lost the race.

## When a cancelled result is visible at all

A cancelled result after a revoke is what the mapping produces when the agent can still see the request. After the student revokes the connection, the agent's credential is dead, so the next protocol call is refused outright rather than answered with `OPERATION_CANCELLED`. Read a refused call as the end of the connection, and expect the structured cancelled result only when the revoke did not take the credential the agent was using.

A cancelled result from `actions.cancel` is different and always visible, because the agent asked for it on a live connection.

## What an agent must never do

Never retry an uncertain outcome under a new key before reading. An uncertain outcome means Coffee Chats cannot tell whether the change landed. A new key is a new change, so retrying under one without reading first can apply the same change twice. Read the current value, and only then use a new key, and only if what is stored is not what was asked for. The [operations](/mcp/recipes/operations) page gives the read that settles each write.

Never treat a permitted result shape as one the server produces. The result contract admits shapes that no tool returns today, including the `requires_user_action` tag. A shape being legal is not a promise that anything produces it. Build against the shapes each tool's own reference page lists, and treat anything else as an unrecognised answer to be reported rather than acted on.

Never infer a reason from a read failure. Every read failure is the same fixed text by design. An agent that tries to distinguish a missing permission from a missing record from a temporary fault is guessing, and its guess will be wrong.

Never keep calling a revoked connection. Once the student revokes, the protocol call is refused and refreshing is refused too. Stop, and ask the student to authorize again if the work still matters.

Never show a raw code to a student on its own. The codes are for the agent. Say what happened and what is stored now.

## Rate limiting is not an error code

A request refused for rate limiting is answered with the status `429` and standard rate-limit headers. None of the codes above appears in that answer. The two limiters and their numbers are on the [operations](/mcp/recipes/operations) page.
